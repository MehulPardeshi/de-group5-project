# BTS on-time flights: source notes

My dataset is the Bureau of Transportation Statistics "Reporting Carrier On-Time Performance (1987-present)" table. It has one row per scheduled domestic flight by a large US airline, with the scheduled and actual times, delays, cancellations, diversions and the cause of each delay. It's the core of our project: it tells us which flights were late and how much of that lateness BTS puts down to weather, which we can then check against the NOAA weather data.

I downloaded the monthly zip files from the BTS pre-zipped downloads page (https://www.transtats.bts.gov/PREZIP/) on November 14, 2026. There are 20 files, one for each month from January 2025 through August 2026, which is the same range as our weather data. They are named like `On_Time_Reporting_Carrier_On_Time_Performance_1987_present_2025_1.zip`. Together they are about 570 MB zipped and 4.9 GB unzipped. Each zip holds one CSV and a `readme.html` describing the columns. The 20 CSVs have 11,730,351 rows in total. The full load on November 18 put exactly 11,730,351 rows into `raw.bts_on_time`, covering every day from January 1, 2025 to August 31, 2026, for 14 airlines and 361 airports. There were no duplicate flights, so `clean.bts_flights` also has 11,730,351 rows.

Each CSV has 109 columns, listed in `raw.sql` with the same names as the header (lowercased). Some examples are `FlightDate`, `Reporting_Airline`, `Tail_Number`, `Origin`, `Dest`, `CRSDepTime`, `DepTime`, `DepDelay`, `ArrDelay`, `Cancelled`, `CancellationCode`, `Diverted`, the five delay cause columns (`CarrierDelay`, `WeatherDelay`, `NASDelay`, `SecurityDelay`, `LateAircraftDelay`), and the `Div1`-`Div5` columns about diversion airports. Every line ends with a comma, so PostgreSQL sees one extra empty field, which goes into a `trailing_empty` column. The loader also adds `source_file` and `loaded_at` so each row can be traced back to its file.

To load the data, I put the zips in `data/bts/` and run `python pipeline/bts/ingest.py` from the repo root. It reads each zip directly with PostgreSQL COPY, so nothing has to be unzipped first, and it checks that the table has exactly as many rows as the CSVs. A few things about the file format matter when querying the raw table. Unquoted blanks load as NULL but quoted `""` loads as an empty string, so blank checks need to handle both. Midnight is written as `2400`. The delay cause columns are only filled in when the arrival delay is 15 minutes or more. Cancellation codes are letters: A is carrier, B is weather, C is the national air system and D is security.

The cleaning happens in `clean.sql`, which builds `clean.bts_flights` from the raw table and leaves the raw table untouched. It turns the text into proper dates, times, whole numbers and true or false values. Midnight written as `2400` becomes 00:00, and every blank becomes NULL whether it arrived empty or as `""`. Each cancellation code gets a readable reason next to it, so B shows up as weather. It also checks for repeated flights, though none turned up. Out of the 112 raw columns it keeps 37, the ones we need for delays, cancellations and the weather join. The rest, such as the diversion airport details, can still be found in raw. Some things I left alone on purpose: delays longer than a day, cancelled and diverted flights, empty cause columns for flights under 15 minutes late, and 147 Southwest flights whose causes don't add up to their delay. Each of these is explained in the quality log. The table has indexes on origin and date and on destination and date, so matching flights to daily weather is fast. Nothing was dropped, so it holds the same 11,730,351 rows as raw.

I tested everything on January 2025 first: 539,747 rows, no duplicate flights, 16,312 cancellations and 1,166 diversions. All 98,130 flights that arrived 15 or more minutes late had delay causes, and the causes always added up to the arrival delay.
